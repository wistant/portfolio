When I decided to rebuild my portfolio, I wanted to move away from standard pre-built landing pages. I aimed to construct a highly optimized, custom design-engineered platform that serves as both a showcase and a package distribution node. 

In this article, I will detail the architectural choices, implementation challenges, and technical mechanisms that power this site.

<br />

### The Inspiration: chanhdai.com

This project’s aesthetic and structural identity is a tribute to [chanhdai.com](https://chanhdai.com/), an exceptional portfolio created by Design Engineer Chanh Dai. I first encountered his work trending on X (Twitter), showing off screen-aligned grid lines, physical micro-interactions, and a custom mouse-tracking canvas cursor. 

Inspired by his pixel-perfect design system, I set out to reconstruct this layout from scratch, adapting it to Next.js 16 (App Router), React 19, and Tailwind CSS v4.

### Technical Choices & Performance Architecture

To maintain high performance while loading heavy visual and interactive assets, I built on a modern, decoupled stack:

#### Next.js 16 (App Router) & React 19
Using React Server Components (RSC) by default allows the server to compile and serialize the main layout and MDX files. This ensures the initial HTML load is extremely small and fast. Only interactive islands—such as the custom cursor tracking, theme switcher, and collapsible listings—are hydrated as client-side modules.

#### Tailwind CSS v4
Tailwind v4 is an architectural shift from v3. By replacing the JavaScript-based `tailwind.config.js` with native CSS variables and `@theme` directives inside a CSS sheet, v4 reduces compile-time overhead. It compiles utility classes directly to optimized CSS variables, improving hot-reloading speed and runtime rendering.

#### Unified Content Layer (MDX + Fumadocs)
Instead of using a separate database or API headless CMS, the blog posts, projects, and certifications are served directly via MDX files in `src/content/`. I built a unified compiler layer around `gray-matter` and `fumadocs-core`. 

Fumadocs parses the file directory structure, reads headings to construct on-the-fly Table of Contents arrays, and automatically exposes raw `.mdx` content endpoints. This makes the text easily digestible for search engines, RSS readers, and LLM web-crawlers (via `/llms.txt`).

### Building a Custom Component Registry

To turn this site into a utility tool for other developers, I built a custom component registry inspired by `shadcn/ui`. This allows me to distribute custom UI components, hooks, and blocks.

```bash
# How to install components directly from our registry
npx shadcn@latest add http://wistant.me/r/theme-switcher.json
```

#### The Compilation Pipeline
The registry operates as a build-step script executed before deployment:

<Steps>
<Step>
**Component Definition:** Components are written in TypeScript under `src/registry/`.
</Step>
<Step>
**AST Parsing:** A compiler script (`pnpm registry:build`) parses the React files, inspects their imports, and resolves their internal dependencies.
</Step>
<Step>
**JSON Manifest Output:** The script outputs JSON files to `public/r/[name].json` containing the component name, required package dependencies (like `motion` or `lucide-react`), and the raw file contents string.
</Step>
</Steps>

This setup lets users import complex animated elements directly into their projects via the shadcn CLI or copy-paste them with a single click.

### Motion, Easing, and Micro-interactions

A design-engineered site relies on micro-interactions. Using static styles feels flat; using slow, linear transitions feels sluggish. I designed a physics-based spring animation system to make the layout feel natural.

#### Target Cursor Physics
The cursor (`TargetCursor.tsx`) uses a custom HTML5 canvas overlays system. It captures window mouse movements and maps them to a GSAP timeline. When hovering over clickable elements, the cursor snaps to their bounds and scales up. 

To ensure the cursor doesn’t lag behind the physical mouse, I synchronized GSAP’s tick updates with the browser’s `requestAnimationFrame` and `Lenis` smooth-scroll ticks.

#### Easing Curve Theme Switches
For the theme switcher, I utilized Framer Motion's layout animations. Instead of fading the background active tab indicator, the element physically slides and stretches to morph into the new tab’s bounds, using a spring curve:

```typescript
// Spring-based layout morphing configuration
transition={{ 
  type: "spring", 
  stiffness: 200, 
  damping: 30, 
  mass: 0.5 
}}
```

### Preventing Cumulative Layout Shift (CLS)

One of the largest contributors to poor Google Lighthouse scores is Cumulative Layout Shift (CLS). When remote or local images load after the main text, they push content down, creating a jarring shift.

To prevent this:
- Every screenshot in the blog is wrapped in our custom `<FramedImage />` component.
- The parent container maintains an aspect-ratio placeholder box.
- Image styles are strictly set with `width: "auto"` and `height: "auto"` to preserve native aspect ratios while fitting container width boundaries.
- Critical above-the-fold assets, such as the dynamic profile avatar (`AvatarLights`), are marked with `loading="eager"` and `fetchPriority="high"` to bypass lazy-loading queues.

### Summary

Rebuilding my portfolio was an exercise in balancing aesthetic layout details with performance guidelines. By using server-side MDX rendering, Next.js App Router, Tailwind CSS v4, and custom GSAP tracking, I built a site that is visually engaging while maintaining a high-performance profile.
